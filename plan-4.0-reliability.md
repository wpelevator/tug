# Plan: 4.0 reliability — backup health contract, safe restic maintenance, operator traps

Working file (see [AGENTS.md](AGENTS.md)). Source: two real-migration reports (backups, and a WordPress move, both on tug 3.1.0), evaluated against `main` (#153) and PR #154, then reviewed by a product-lead/architect pass. This plan assumes PR #154 is merged and starts from `main`; it does not stack on that branch. All work ships as one pull request from `main` (branch `feat/4.0-reliability`); the "version packages" PR is held until it merges, so 4.0 is not tagged without it.

## Already true (do not rebuild)

- With no `x-tug.health` no readiness probe runs, so "no check by default" is today's behaviour and the docs say so. An image `HEALTHCHECK` still gates `depends_on: service_healthy` (`reconciler.ts`). Add a lock-in test only.
- `backup password` before the first deploy, `destination check`, `rest:` docs and the restic-adoption note in `docs/migration.md` are on `main`.

## Decisions

1. **Only the `--check` change is a 4.0 item.** `backup list --check` starts failing on retention and lock problems, which changes what an existing monitor's exit code means, so it ships in the major together with its opt-out. Everything else here is additive and ships as minors or patches.
2. **Retention is structured data.** A run stores `retention: { state: ok | failed | external, message? }` (redacted) in `backup_runs.metadata_json`, next to the existing `warnings`; control backup stores the same in `backups.metadata_json`. No migration and no new column, so the 4.0 upgrade note's "changes no table" stays true. `GET /api/v1/backups` returns explicitly parsed fields at target level (`retention`, `lock`, `cause`); the raw `metadata_json` string is not part of the frozen `--json`, and the upgrade note says so.
3. **`--check` fails after two consecutive retention failures** on a target (or one failure with a restic lock exit), not one: on a multi-node project a prune takes an exclusive lock on the shared repository while another node's backup holds a shared one, so a single overlap is harmless. A recovery clears it.
4. **Lock failures are classified by exit code, never by wording.** restic 0.17+ exits 11 when it cannot lock. A run that exits 11 is recorded with `cause: "locked"`; holder and age from restic's message are best-effort display only (the codebase refuses to match wording, `repository-probe.ts`). A locked run is still a failed run and emits the existing `backup.failed` event with `cause: "locked"` in its metadata. There is no separate `backup.locked` event.
5. **Append-only is a destination setting.** All projects and the control repository share one destination. `tug backup destination set --retention external` (admin) stores the mode with the destination; it skips `forget --prune` for every project and for the control backup and records `retention.state: external`. No per-target `x-tug` key in 4.0. Docs state what the operator then owns: pruning from the storage side, the `--keep-tag trigger:pre-restore` protection (`job.ts`), and that cleanup of partial snapshots will fail. Without the setting, an append-only server shows as a retention failure, which is the intended signal. The upgrade note says an append-only user's `--check` goes red after 4.0 until they set it.
6. **Events and webhooks.** Add `backup.retention_failed` and a matching recovery event (compare `node.recovered`), emitted on transition only, where the previous state comes from the prior successful run's `metadata_json`. Add both to `TRANSITION_MESSAGES` in `notifications.ts` so webhooks deliver them.
7. **tug must stop killing restic.** `removeContainer` force-removes the helper on abort, timeout, the stall watchdog and leftover cleanup after an agent restart, which can SIGKILL `forget --prune` while it holds the exclusive lock and leave a stale lock that blocks every later backup. Send SIGINT/SIGTERM and wait a short grace period before removing the container. The stall limit (`RESTIC_STALL_MS`, 10 min) must exceed the lock wait (`--retry-lock`, 10 min), otherwise a lock wait is reported as a stall; set it above and test against real restic.
8. **Stale locks: report, then an operator command.** tug never unlocks on its own (a lock may belong to a live prune on another host). The locked-run message names the fix, `tug backup unlock [--control]`: plain `restic unlock` (never `--remove-all`), `admin` role, audited, holds the project lock, runs in the agent's per-project job lane, new agent command type in `BACKUP_COMMAND_TYPES`. restic's `unlock` removes only locks that have gone stale. No free-form restic passthrough: the helper holds the destination credentials shared by every project and `_control`, and flags such as `--password-command`, `-r` or `-o` would turn a deploy-role credential into code execution and cross-project access. Operators who need raw restic use `tug backup password` (admin).
9. **No delete-permission probe.** On a versioned S3 bucket a DELETE of a missing key creates a delete marker, tug has no S3 client, and the `rest:` answer depends on server internals. `destination check` reports only whether `--retention external` is set.
10. **Naming.** The new verification command is `tug backup verify` (`backup.check` is already the destination probe's agent command, and `destination check` and `list --check` exist).
11. **Maintenance moves to a schedule.** `forget` stays per run; `prune` and `verify` (`restic check`, optionally `--read-data-subset`) run once per repository on a weekly schedule, which removes the prune contention at its source and closes the roadmap's "weekly maintenance" item. A target's verify result is recorded per target.
12. **Protection levels have strict meanings.** `off-host`: the destination is not a local path and the target has a recent success. `verified`: a `restic check` covering the target ran after its latest snapshot. `restore-tested`: a scratch restore of the target succeeded (`restore_runs` already records mode and state). `backup list` shows the level. If per-target verify results need storage the `backups` table cannot hold, add one migration step in `src/db/db.ts` with a previous-release fixture and correct the "changes no table" line.
13. **Repository size and snapshot count are not in `backup list`.** They need `restic stats --mode raw-data` per repository under a lock. Deferred; `verify` may report them.
14. **`deploy --hold`.** `tug deploy --hold <services>` publishes the deployment with the named services held (holds are inserted at publish; the agent stops held services). Held means stopped, not unchanged, and holds persist across later deploys; both are documented. The `deploy` role may release a hold whose reason is `deploy hold` so a CI credential cannot place a hold it cannot remove; all other holds stay `admin`. The migration guide's deploy-then-import sequence (`migrating-from-compose.md`) uses it, because between those steps a WordPress app runs against an empty database and exposes its installer; until it ships, document deploying with ingress off.
15. **Ingress preflight.** `node add --ingress` over SSH checks that 80 and 443 are free (reuse the `controlPortCheck` pattern in `install.ts`), exempting tug's own Caddy and control on the node, and fails before changing anything. For an existing node, `tug node ingress` only flips a control flag, so a bind failure is reported in `ingress_status` instead of a new agent round trip.
16. **Lint hint.** `tug lint` warns when a volume that backs a database service or a `backup` target is not `persistent: true`; a warning, silenced by an explicit `persistent: false`.
17. **Restore cleanup.** `tug restore list` shows scratch volumes and safety snapshots; `tug restore remove <id>` and `--expire-safety <age>` delete them (`admin`, project lock). Safety-snapshot expiry fails on an append-only destination and says why.

## Checklist

- [ ] Open one PR from `main` on `feat/4.0-reliability`, one commit per unit in table order
- [x] WU2: SIGINT/SIGTERM with grace before container removal on abort, timeout, stall and restart cleanup; stall limit above lock wait; integration test that a killed prune does not leave a lock that outlives the grace period. Notes: signals go to restic inside the helper (`pkill -INT -x restic`, then TERM) because `docker stop` would only signal the helper's PID 1 (`sleep`), not the exec'd restic; `stopResticGracefully` in `job.ts` is shared by job, control backup and both leftover cleanups; the stall limit is 15 min (lock wait 10 min); the control backup's own stall watchdog counts only retry notices, which a lock wait does not print, so it is unchanged. The integration test (`tests/integration/restic-stop.test.ts`) holds a lock with a stdin backup rather than a real prune and also proves removal alone leaves the lock.
- [x] WU1: structured `retention` and `lock`/`cause` in run and control-backup metadata; exit-11 classification; explicit parsed target fields in `GET /api/v1/backups`. Notes: the agent reports exit 11 as `cause: "locked"` on a failed result and `retention: {state, message?, locked?}` on a successful one (`locked` marks a prune that exited 11); `GET /api/v1/backups` also drops each run's raw `metadata_json` and serves parsed `retention`, `cause` and `warnings` per run; target `retention` adds a `failures` streak; `lock` is `{message?}` while the newest run hit exit 11
- [x] WU1: `--check` two-strike rule and recovery; `backup list` prints retention and lock state; `--json` fields frozen and listed in the upgrade note. Note: the plan's "opt-out" for the `--check` change is the destination `--retention external` setting; no separate `--check` flag was added
- [x] WU1: `destination set --retention external` (stored with the destination, applies to projects and control), `destination show`/`check` report it; `backups.md` append-only section; upgrade note says append-only users must set it. ## Out of scope

`x-tug.release`, `tug move`, webhooks beyond the events above, builder nodes, M16 grants, MCP, a free-form restic passthrough, repository size in `backup list`, a per-target `x-tug.backup.retention` key.
