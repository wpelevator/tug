The agent and the control plane keep their state in Docker volumes instead of host directories, so a node or control host holds nothing a rebuild cannot recreate and moving to a new VM needs no host files. **Existing hosts must migrate first:** after upgrading the CLI run `tug node migrate --all` (or `tug node migrate <node>`) for every node and `tug control migrate <ssh-target>` for the control host, before any other `node add`, `node replace`, `node repair` or `control setup`, which now refuse a host that still keeps its state in `/var/lib/tug` or `/var/lib/tug-control` and name the command to run. Migration stops the old container, copies the state into the `tug-agent` or `tug-control` volume with its modes, keeps the node key and the control CA, starts the new container on the volume and starts the old one again if the copy fails; the old directories stay as a fallback and are yours to remove. `node add` no longer writes `/etc/tug/agent.env`: a connect-only control URL is passed to the agent as `TUG_CONTROL_URL` and carried over by `node migrate`, and tuning variables set by hand in that file are not. Preflight checks free space under Docker's data root instead of `/var/lib`, `node remove --teardown` always removes the `tug-agent` volume with the node key, control restricts its data directory to mode `0700` itself, and `tug deploy` warns about absolute bind mounts, which tie a service to one host.
