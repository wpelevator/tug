'@wpelevator/tug': minor
---

Docker Compose is no longer needed anywhere. `tug control setup` starts the control container with `docker run` instead of a Compose file, so the control host needs only Docker Engine: the preflight no longer checks for the Compose plugin and `--install-docker` no longer installs it. Running `control setup` again recreates the container on the `tug-control` volume and removes the Compose file and network of an earlier install; `tug control migrate` is unchanged and, as before, only applies to hosts that still have the Compose-based install. `tug deploy` reads the Compose file with its own reader instead of running `docker compose config`: interpolation (including `${VAR:-default}` and `${VAR:?error}` and `.env`), `env_file`, `extends`, profiles and short syntax, checked against `docker compose config` on the shipped examples and a fixture corpus. A file that uses `include` or an `!reset`/`!override` tag is rejected with an error that points to the new `tug deploy --compose-cli` (or `TUG_COMPOSE_CLI=1`), which renders it with `docker compose config` as before. Two behaviours differ on purpose: a `command` string containing a shell operator such as `&&` is now an error instead of being silently cut off, and a relative `env_file` path is resolved against the Compose file's directory. `tug doctor` no longer reports `docker_compose`.
