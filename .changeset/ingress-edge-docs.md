The managed ingress keeps requests and WebSockets alive across upstream churn and tells clients what is happening. A request retries for up to five seconds when no upstream is available instead of returning a 502 at once, and open WebSockets keep running for up to five minutes after a config reload instead of being cut on every site whenever any site deploys. A host with no serving upstream now answers `503` with `Retry-After` instead of failing the TLS handshake, and the new `x-tug.ingress.maintenance: true` does the same on purpose without restarting the service. Because the 503 host keeps its site block, Caddy now also requests a certificate for it; use `tls: off` while DNS is not ready. Caddy's per-host Prometheus metrics are available on the ingress node's loopback admin endpoint, and `TUG_INGRESS_ACCESS_LOG=true` turns on a JSON access log per site (off by default, since URLs and client IPs are logged). The new directives need a current Caddy 2 image: an ingress node that cached an older `caddy:2-alpine` must pull a newer one or set `TUG_CADDY_IMAGE`. The ingress docs also list the proxy's remaining limits and compare it with kamal-proxy, Uncloud, Traefik and Dokku.
