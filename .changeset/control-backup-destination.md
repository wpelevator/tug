Control now backs itself up to the shared backup destination. Once `tug backup destination set` has run, control stores a consistent archive of its database, private CA and master key (without build images) in a `_control` restic repository every night, retries a failure after an hour and keeps 3 recent, 7 daily, 4 weekly and 6 monthly snapshots. Status and scheduling follow the destination in use, so switching destination starts a backup there and shows it unprotected until it completes, and a local-path destination is labelled local only. The repository has its own password, derived from the master key like each project's, so a node that holds the destination credentials cannot read or forge it; `tug backup password --control` prints it for escrow.

`tug control backup --offsite` stores a backup in the destination now and prints the snapshot id, `tug control backup list` shows the copies on the host and the snapshots really stored in the destination, `tug control restore --from-destination <url> --env … [--snapshot <id>]` rebuilds control from that repository (credentials and `TUG_CONTROL_BACKUP_PASSWORD`), `--from-file <file>` uploads a local archive instead of requiring it on the control host, and `--verify` checks a backup without applying it. `tug control backup --download [-o <file>]` saves a `0600` copy on your machine and says what was saved and where the server copy remains.

A restore now replaces the database, master key and CA as one step that is rolled back if interrupted, works in a private scratch directory (`TUG_CONTROL_RESTORE_DIR` is only its parent, and startup never removes anything Tug did not mark as its own), and retires the commands and workload restores the backup carried so that a restored control does not replay them. New routes: `GET /api/v1/control/backups` and `GET /api/v1/control/backups/:id/download`; `POST /api/v1/control/restore` also accepts an `application/gzip` upload. Creating, downloading and reading the password of control backups are audited.
