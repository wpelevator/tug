Add `build.secrets` as standard Compose secrets, and `build.additional_contexts`. A build lists keys of the top-level `secrets:` (`- npm_token`, or `{ source, target }` where `target` is the BuildKit id), exactly as `docker compose build` reads them, so the same file builds with plain Compose. Each declaration resolves to a tug project secret: `x-tug.secret`, then the `name` of an `external` secret, then `environment`, then the declaration key. A `file:` or `environment:` source is for plain Compose only and tug never reads it. A mapped secret that is missing fails the deploy with the exact `tug secret set` command (with `--from-file` when the declaration names a file), and a name that exists only as a variable is refused. `content:`, a templated `name:`, a mapping to `TUG_REGISTRY_AUTH`, an undeclared reference and a service-level `secrets:` are rejected. Control hands the values to BuildKit through its environment, so they are in no image layer, process argument, build error or deployment record, and a service that uses them builds on control, not with `--build-local`. `tug deploy --dry-run`, the deploy report and `tug values` list each used declaration with its mapping and the ignored local source. `build.additional_contexts` passes named contexts (`COPY --from=name`) and needs `docker buildx` where the image is built; without it the deploy fails with a message that says so.
