Version skew now travels with ordinary traffic instead of a paid preflight: the control stamps every HTTP response with its version (`x-tug-version`) and refuses any request declaring a newer client version (`x-tug-client-version`, sent by the CLI and the agents on every request) before running the handler — so a CLI ahead of the control is stopped by the surviving side itself, and read commands (`ps`, `status`, service listing) get the version check for free on their own response without the dedicated `GET /api/v1/version` request every command used to make per process. Only commands whose first control request is a mutation (`deploy`, `rollback`, `restart`, `backup`, restore), live commands (`exec`, `run`, `logs`) and `node add` still take the one-request explicit probe, because a mutating request must never already have been received by an old control when the refusal arrives. The version route stays, and a control older than the stamping feature is refused from its missing stamp with the same `tug control setup <control host> --yes` remediation as before; a CLI behind the control still proceeds with the one-time `npm i -g @wpelevator/tug@<version>` pin warning.
