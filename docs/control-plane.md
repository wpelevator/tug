# Control plane

## Install over SSH

```bash
tug control setup root@control.example.com
```

The address clients use by default comes from `controlUrl` in the CLI config file (`--config <file>` selects one), including any overlay override. Without it, the address is the SSH target's host plus the published port (`https://control.example.com:8443`), which `control setup` prints. Pass `--control-url` (or set `TUG_CONTROL_URL`) to override either default, for example when you install through an SSH alias or a private address but clients reach control elsewhere. The credential URL is never used as an installation address. A configured URL keeps its public port even when `--port` publishes a different Docker host port. It is only an address: clients verify the generated control name, not this URL. `control setup` runs SSH preflight checks on the host (Docker, at least 2048 MB free under Docker's data root, the mTLS port free), then starts the `control` container with `docker run` from `src/templates/control-install.sh` (no Compose plugin is needed), publishing one port (default `8443`) and mounting the `tug-control` volume. Running it again recreates the container on the same volume with only the flags you pass (a port or extra name you leave out resets to its default), so upgrade with [`tug control upgrade`](#upgrading-the-control-plane) instead (setup prints a note when its flags would change the settings of a control already there); `setup` on an existing install also removes the Compose file and network of an install made before control stopped using Compose. Add `--install-docker` to install Docker Engine first on a supported Debian, Ubuntu, Fedora and RHEL-compatible host.

On a fresh install it then issues the **root** credential on the host (`docker exec ... control issue-credential --name root --role admin` over SSH) and imports it straight into the local config as a `0600` file (`--credential-out <file>` optionally writes an extra copy; there is no default file); it never lands in container logs or a permanent file on control. Upgrading with `control upgrade` (or running `control setup` again) preserves credentials and never reissues root. If the root credential is lost, `tug control setup <ssh-target> --control-url https://control.example.com:8443 --recover-root` replaces only root's key without the API, closes its sessions within a second and audits the recovery; other admins are unaffected.

The control container runs the published image `ghcr.io/wpelevator/tug:<CLI version>` (the installed CLI's own package version, so control and the CLI match). Pass `--image <tag>` to use another tag, or `--build-local-image` to build the image from the current checkout and copy it to the host over SSH with `docker save` / `scp` / `docker load` (tagged `tug:local` unless `--image` is given); the latter is for development and needs the repository's Dockerfile in the working directory. See [Releases](releases.md). `control setup` over an existing control also replaces it in place: the port preflight accepts the port when the existing `tug-control-control-1` container holds it, and still fails when anything else does.

Built images always travel as compressed archives over the authenticated control connection. Published `image:` services pull directly from their upstream registry by the digest resolved on control before deployment publication.

`control setup` (also available as `tug setup <ssh-target>`) imports the root credential into the local config automatically, the same way `tug init` does, so no separate step is needed. In a terminal it shows a plan and asks for confirmation (`-y, --yes` skips it) and offers to install Docker when it is missing. `--no-import` skips the import. To import a credential from elsewhere (for example one issued on another machine), run:

```bash
tug init root.credential.json
```

`tug init` copies the credential (a file, or `-` for stdin) into a `0600` file under `~/.config/tug/credentials/`, named `<control host>_<port>.<ca12>.json` where `<ca12>` is the first 12 hex characters of the CA's SHA-256 fingerprint with colons removed, and points the git-ignored `tug.local.yml` at it. The CA fingerprint in the name makes importing a credential from a different control CA additive: it writes a new file and cannot overwrite the credential the CLI was working with, while a same-CA re-issue (for example a root recovery) keeps the same file. Importing across CAs prints a notice that names both fingerprints. CI passes `TUG_CREDENTIAL` (the encoded credential) or `TUG_CREDENTIAL_FILE`; precedence is `--credential <file>`, then the environment (setting both is an error), then the overlay's `credential` path. Tracked configuration may not name a credential.

A release publishes the npm package a few minutes before its container image. A freshly updated CLI therefore fails `tug setup` and `tug node add` before touching the host, with a message that the image is not published yet; retry shortly, or pass `--image ghcr.io/wpelevator/tug:latest`.

## Authentication and PKI

Control listens on **one** TLS 1.3 port that requires a client certificate from every peer. There is no plain HTTP listener, no unauthenticated route (not even a health check: monitor TCP reachability separately from authenticated readiness) and no bearer token. Operators, CI and nodes all use certificates signed by control's private CA; see [Access control](access-control.md) for identity classes, roles and key-based authorization.

- **CA.** A self-signed P-256 CA (10-year lifetime) is created only for a fresh installation and kept at `<data dir>/pki/ca.key` (`0600`) and `ca.crt`. Missing, corrupt or mismatched CA material alongside existing state is a startup error. CA rotation is out of scope; replacing the CA means redistributing trust and credentials.
- **Control name.** Control has a generated name, `control-<first 12 hex of the CA key hash>.tug`, derived from its CA. It is stable for the life of the CA, needs no configuration and survives backup and restore with `pki/`. Clients recompute it from the CA they pin and verify the server against it, so verification never depends on the address they dial.
- **Server certificate.** SANs are the control name, the host of `TUG_CONTROL_URL` (required, a credential-free `https://` origin including the published port; the default address written into credentials) and optional `TUG_EXTRA_SANS` (comma-separated DNS names and IPs). The server certificate lasts 90 days, is renewed at two thirds of its lifetime while running, and the TLS context reloads without a restart. Control warns when the CA nears expiry.
- **Profiles.** Control assigns every certificate: it verifies CSR signatures and P-256 keys and never copies requester-supplied subjects, SANs, validity or extensions. Leaves are `CA=false` with one assigned identity URI, back-dated five minutes and capped by the CA's validity.
- **Connections.** Chain validation rejects missing or foreign certificates during the handshake, before any HTTP is parsed. TLS session resumption is disabled and any reused session is closed, so every connection presents its certificate. A post-handshake gate then checks the database, and every request and WebSocket upgrade checks it again. Disable, replace, remove, revoke, root recovery and certificate expiry close the affected sockets (API-originated changes immediately, host-side changes within a second).
- **Clients.** The CLI and agent pin the credential's CA and verify the control name derived from the CA. `--control-url` / `--agent-control-url` change only the TCP connect target (for example `127.0.0.1:18082` through an SSH tunnel), and the credential's stored URL is just the default target. Moving control to a new IP or DNS name therefore invalidates no credential; see [Moving the control plane](#moving-the-control-plane).

Deployment boundaries: TCP passthrough works. TLS termination ahead of control does not (it breaks the client certificate), and TLS interception fails certificate validation. Browsers need explicit CA trust and an imported client credential; browser setup is out of scope. Control's mutual TLS does not encrypt workload traffic between nodes; that traffic uses the operator's network ([Networking](networking.md#bring-your-own-network)).

### Backups and authorization history

`control backup` includes `pki/` (except the regenerable server certificate) and the key bindings. Restore validates the CA before changing live state, closes live sessions and requires a restart. Because authorization follows keys, a snapshot older than a certificate renewal does not lock a node out. An older snapshot still forgets nodes and operators created after it, restores keys that were replaced afterwards, and revives principals disabled or revoked afterwards. After an older restore: recover root on the host if needed (`--recover-root`), reapply revocations and disables, run `tug node replace` for nodes whose key changed and `tug node add` for nodes created after the snapshot (`tug node replace --all` after a CA loss).

## Image delivery without a registry

Remote builds save immutable images under `<data dir>/images/<build ID>.tar.gz`. Agents download only the images assigned to them through `GET /agent/v1/images/:buildId`, verify the compressed SHA-256 and byte count, validate the saved image metadata and load the archive. The agent loads those artifacts without a registry pull. No registry certificate, daemon trust change or inbound connection to a node is needed; downloads use the same mTLS connection as every other agent request.

`tug deploy --build-local` builds application images on the operator machine and uploads archives instead of source. Control validates and imports them, gives them immutable tags and serves them to assigned agents. Builds are single-platform Linux images (amd64 or arm64); use a Docker builder matching target nodes. Agents reject an incompatible image platform before starting it. This flag is distinct from the installers' development-only `--build-local-image`, which builds the Tug runtime itself.

All published desired-state history is retained, including rollback and lagging-node references. Its image archives remain available until you run `tug image prune`, which deletes the archives of everything except the newest `--keep N` (default 5) distinct builds of each project (deployments that reuse an archive count once), the current deployment and any version a node still reports; `--dry-run` lists what would go. The desired states stay in history, but rolling back to one whose archive was pruned is refused and the service must be deployed again. A rebuild whose image ID equals one the project already has an archive for (the Docker layer cache made it identical) reuses that archive: the new deployment points at the existing build, no second archive is saved and the new per-deployment tag is removed. Nodes already hold that image, so they download nothing and the running container is kept; only a changed image adds an archive. After each successful deploy control also runs the same prune automatically, keeping the newest `TUG_IMAGE_KEEP` distinct builds per project (default `5`, `0` turns it off), and caps the Docker build cache with `docker builder prune --all --keep-storage $TUG_BUILD_CACHE_KEEP` (default `10GB`, `0` turns it off); see [Configuration](configuration.md#control-plane). Both run after the response and only log a failure. `tug image prune` remains for a one-off prune with a different `--keep`. Cleanup removes failed unpublished builds and orphan archives. Agents prune only their recorded, unused Tug images absent from their authorized retained set and never run global Docker prune; an image whose archive was pruned leaves that set (rollback to it is refused), so pruning on control also frees the disk of nodes once no container uses the image. Each changed image is stored and transferred as a complete compressed image, with no layer sharing between archives.

## Published images and private registries

Control resolves each distinct published image tag once per deployment through the registry HTTPS manifest API and stores its SHA-256 digest in both desired service state and canonical Compose. Multi-platform images retain their complete index digest, allowing each node to select its architecture from that same immutable index. An explicit SHA-256 pin is validated and kept without a network lookup. If resolution fails, the deployment fails before replacing current desired state. Rollback and scaling reuse the stored pins without resolving tags again. Registries must retain pinned manifests and layers for rollback and fresh-node pulls; Tug does not mirror published images.

Private registry credentials live in the encrypted project secret `TUG_REGISTRY_AUTH`, a JSON object keyed by registry host (including a port when applicable):

```json
{"ghcr.io":{"username":"ci-user","password":"pull-token"},"docker.io":{"username":"hub-user","password":"hub-token"}}
```

Store it using `tug secret set TUG_REGISTRY_AUTH --project site` with the value on stdin. Use `docker.io` for Docker Hub, including short image names. HTTPS registries with Basic or Bearer authentication are supported; credential helpers and plaintext registries are not. Use credentials with pull access only. Control decrypts the secret for resolution; assigned agents receive only credentials for their published image hosts through the authenticated secrets endpoint and pass them directly as Engine API `X-Registry-Auth`. Credentials stay out of desired state, container environments and Docker login files; referencing the reserved secret in a service definition is rejected. Secret updates apply to future pull requests, including retries and rollback; keep access to retained image digests when rotating credentials.

Tug issues one node identity (key and certificate) per node. It does not push built images, manage registry users or log agents into registries. Teams building images in CI can push them themselves and deploy with `image:`.

## Backup and restore

`tug control backup --local` takes a consistent SQLite snapshot (including operator credential records) and writes a `0600` `.tar.gz` (in a `0700` directory) with `tug.db`, `master.key`, `pki/` (the private CA), retained `images/` archives (leave them out with `tug control backup --local --no-images`; deploy again to rebuild them after a restore) and metadata to `TUG_CONTROL_BACKUP_DIR` (default `<data dir>/control-backups`). `tug control restore <artifactRef> --confirm` overwrites the database, master key and image store from such an archive; restart control afterwards. SQLite snapshot creation and restore integrity checking run synchronously and pause control API traffic, WebSocket handling and timers. Duration grows with data size and storage speed; the synthetic benchmark and reference measurements are in [Testing](testing.md#sqlite-contract-and-blocking-measurements). Take larger backups outside latency-sensitive rollout windows and keep project lease durations above expected blocking time. Restore validates through a read-only connection before replacing live data, then rejects database-dependent requests with HTTP 503 until restart. This is the control-plane backup: it covers disaster recovery of the control plane only and does not capture workload volume contents. Back up project data (volumes, databases) with `x-tug.backup` as described in [Backups](backups.md). Once a backup destination is set, control also stores a nightly archive of itself, without images, in the `_control` repository of that destination (see [Control plane backup](backups.md#control-plane-backup)); `tug control backup --download [-o <file>]` takes an on-demand copy to your machine.

Running containers keep serving while control is down; agents just cannot pick up new desired state until it is back.

### Recover control on another host

For a planned move of the whole installation, including workloads, see [Migrating to new servers](migration.md).

This procedure was exercised with the published 0.9.0 release on two VPSes and again on the 1.0.0 candidate on QEMU VMs, onto a different host with the original credential and a `node replace` to repoint the agent; see [Real-host evaluation](real-host-evaluation.md#recovery-drill-with-the-published-090-release-2-november-2026) and [the 1.0 drill](real-host-evaluation.md#recovery-drill) for the exact scope and limitations. Keep the control's public host name when you move it (the credentials verify that name); only the connect address may change. Restore the workload data separately using its project backups. Keep the control backup encrypted off-host and keep the original operator credential and backup repository passwords separately; the control archive contains the master key and private CA.

1. Stop or isolate the old control plane before directing agents to the replacement. Two active control planes with divergent state are not a supported failover setup. Running workload containers continue serving while control is unavailable.
2. Install the matching Tug release on the replacement host with `tug control setup`, writing its temporary bootstrap credential to a private file. This initializes a new control and CA solely to authorize the restore.
3. Choose where the backup comes from. From a file you kept (for example `tug control backup -o recovery.tar.gz`), decrypted: `tug control restore --from-file recovery.tar.gz --confirm --credential <bootstrap-credential>` uploads it to the new control, so nothing is copied by hand. From the shared destination, no file is needed: `tug control restore --from-destination s3:https://s3.example.com/bucket/tug-backups --env AWS_ACCESS_KEY_ID --env AWS_SECRET_ACCESS_KEY --confirm --credential <bootstrap-credential>` has the new control read the newest `_control` snapshot (`--snapshot <id>` picks another from `tug control backup list`). The destination credentials and the control password you escrowed with `tug backup password --control` come from your environment (`TUG_CONTROL_BACKUP_PASSWORD`), or pipe the password in with `--password-stdin` and keep the credentials in the environment, and are used for this restore only. Run the same command without `--confirm` first: it only checks the backup and prints what it holds. An archive already on the control host also works: `tug control restore /data/restore-input.tar.gz --confirm`.
4. Restart the control container. Restore replaces the bootstrap CA, credentials, state and image store; the temporary credential no longer authenticates after restart. The database, master key and CA are replaced together: if the restore is interrupted, the previous state is put back at the next start. Commands that were queued or running when the backup was taken are retired at that start instead of being delivered again, and the workload backup runs they carried are closed as missed or failed. No file from the old host is needed, only the backup, the destination credentials and control password when restoring from the destination, and your original operator credential.
5. Connect with the original operator credential and use `--control-url https://<replacement-host>:8443` if the address changed. Verify the recovered projects, deployments and backup catalog. Agents that still point to the old address must be repointed; the tested 0.9.0 path was `tug node replace <node> <ssh-target> --control-url https://<replacement-host>:8443 --agent-control-url https://<replacement-host>:8443 --credential <original-credential>`. Verify that each node returns online and that the site serves the expected data.

A snapshot older than later node or operator changes does not contain those changes; follow the identity and revocation recovery notes in [Authentication and PKI](#authentication-and-pki). This sequence does not replace a separate, tested backup of workload volumes or databases.

## Upgrading the control plane

Tug trusts [semver](https://semver.org). The **compatibility key** of a version is its major, or the whole `0.minor` while the major is 0 (semver promises nothing for 0.x, so any minor may break). Control, CLI and agents interoperate when their compatibility keys match: inside one major a newer minor only adds, and a patch never changes what they say to each other. See [Choosing the bump](releases.md#choosing-the-bump) for how releases keep that promise. The check itself travels with ordinary traffic (the Docker `/_ping` bargain: version information rides headers, not dedicated round trips):

- The control stamps every HTTP response with its version (`x-tug-version`), so clients know what is answering them without a probe.
- Every CLI and agent HTTP request to the control declares the process's own version (`x-tug-client-version`; requests to anything else, such as agent health checks against your containers, never carry it); the WebSocket upgrades carry it too, but upgrade handling does not gate on it. The control refuses any request declaring a version on a newer compatibility key than its own **before running the corresponding handler** (from 1.0, a client with a newer minor of the same major is served) — so a CLI ahead of the control is stopped by the surviving side itself, and an agent is refused rather than allowed to talk down what it assumes, matching the upgrade order below.
- A CLI grants itself the read-direction rule: read commands (`status`, service listings) judge the stamp on their own responses; since reads are safe to have run against an older control, they pay no extra request. Commands whose first control request is a mutation (`deploy`, `rollback`, `restart`, `backup`, restore), live commands that open the live channel without a read first (`exec`, `run`, `logs`, `ps`, `inspect` given an explicit node or running non-interactively), and `node add` take a one-request explicit probe (`GET /api/v1/version`) instead, so a mutating request is never already received by an old control when the refusal arrives.

Remediations:

- The control is older than the CLI (a missing stamp on a command's own read reports this too — the control predates both stamp and probe): the command is refused with `tug control upgrade <control host> --yes` as the fix. That redeploys the control container at the installed CLI's image tag and preserves the state and PKI in the `/data` volume.
- The CLI is older than the control: inside the same compatibility key it just works (from 1.0, an older minor needs nothing). Before 1.0 it proceeds with one warning naming `npm i -g @wpelevator/tug@<version>`. A control on a newer **major** than the CLI refuses the command with that same pin command, since the control no longer supports it.
- The CLI is a newer minor than the control inside one major: commands work unless one needs a route added in that minor, which fails with the control's 404 explained by `the control runs X, this CLI is Y … tug control upgrade <control host> --yes`.

Rolling the control back below the agents' version is refused the same way: an agent newer than its control gets the control's refusal on every poll, logs it with the remedy, and keeps its containers running without reconciling until the versions agree. So roll the control back together with the agents (`tug node upgrade --all` with the older CLI, or `--to` the control's version), or upgrade the control again, rather than leaving agents ahead of it.

The control's database upgrades itself when the new control starts: it copies a database that holds data to `tug.db.pre-v<N>.bak` in the data directory, runs the pending schema steps and records the version. From 1.0 an older control refuses a database from a newer one with one `error:` line in its log that names the schema versions (Docker keeps restarting the container until you act), so a rollback across a later schema change needs the pre-upgrade state: stop the control, put the `.pre-v<N>.bak` copy back as `tug.db` (or restore a control backup taken before the upgrade) and start the older image. Schema 1 is the schema every release from 0.8 to 1.1 shares, so rolling the 1.0 control back to 0.14 opens the same database (verified, see [Real-host evaluation](real-host-evaluation.md#rollback-lane)). Schema 2 (the `project_domains` table of `tug domain`) arrived in the release after 1.1.0: once that control has opened a database, 1.1.0 and older refuse it, and rolling back means restoring the `tug.db.pre-v2.bak` copy or an earlier control backup, which discards every deployment and mapped domain made since the upgrade. A minor release that changes the schema says so in its changelog.

**The upgrade command.** `tug control upgrade [<ssh-target>] [--to <version>]` is the one step for a new release: it reads the running container (published port, advertised URL, extra names), tags the image it replaces as `tug:rollback`, starts the new image on the same `tug-control` volume, checks that the CA on the volume did not change and waits for control to answer with its version. The SSH target is `controlSsh` in `tug.yml` when not given. It never touches the data, so a failed start leaves the previous image one `tug control upgrade --rollback` away (which redeploys `tug:rollback`; across a schema change the older control refuses the migrated database, see the paragraph above). `tug upgrade` runs it and then `tug node upgrade --all` in the order below.

Confirm the upgrade with `tug doctor` and `tug ps` right after, then match the agents with `tug node upgrade --all` (see [Upgrading an agent](nodes.md#image)); see the [mismatch runbook](troubleshooting.md#cli-control-version-or-credentialca-mismatches) when `tug doctor` reports a CA fingerprint mismatch.

## Moving control data into the volume (`control migrate`)

Control installed by an earlier release keeps its data (database, master key, CA, build archives) in the host directory `/var/lib/tug-control`; since then it keeps it in the Docker volume `tug-control`, so nothing on the host is needed to move or rebuild the control host. `tug control setup` on such a host refuses, naming this command, because a new install would start on an empty volume and create a second CA.

```bash
tug control migrate root@control.example.com
```

It rewrites nothing you chose: control keeps its image, URL, port and SANs. In order it stops control (never removes it), copies the directory into the volume as root with modes and SQLite files intact, writes a version marker into the volume last, points `/opt/tug-control/docker-compose.yml` at the volume, starts control again and waits for its CA. If the copy fails the old control is started again and the Compose file is untouched; rerunning after any failure finishes the job. The old directory is left in place as a fallback and holds a copy of the master key and the CA, so remove it once control is confirmed healthy. Control stays on the image it was running, so the `0700` restriction control now puts on its data directory applies once `tug control setup` upgrades it, which works as before after migrating.

## Moving the control plane

Because clients verify the generated control name, the address is only a default:

1. Move or re-address the host and set the new `TUG_CONTROL_URL` on control (or rerun `control setup` with the new `--control-url`). Control adds the new address to its certificate on restart.
2. Until credentials are refreshed, point clients at the new address: `tug --control-url https://NEW:8443 ...` or `TUG_CONTROL_URL`, and for an agent rerun `tug node add <node> <ssh-target> --agent-control-url https://NEW:8443`, an idempotent upgrade that keeps the node's key and passes the new address to the agent as `TUG_CONTROL_URL`.
3. Optionally reissue credentials so they carry the new default: `control setup --recover-root` for root, `credential create` for others, `node replace` for nodes.

No credential becomes invalid because the address changed. The control name only changes if the CA itself is replaced, which requires redistributing every credential.

## Lost or compromised something

| Situation | What to do |
| --- | --- |
| Lost the root credential | `tug control setup <ssh-target> --recover-root` |
| A CI credential leaked | `tug credential revoke <name>`; live sessions close within a second |
| A node is suspect | `tug node disable <node>` now, then `tug node replace` |
| A node's identity is corrupt or expired | `tug node repair` or `tug node replace` |
| Restored an older control backup | Recover root if needed, reapply revocations, then `node replace --all` ([Control plane](control-plane.md#backups-and-authorization-history)) |

## Access control

Besides the `root` admin credential, control accepts named operator credentials with `read`, `deploy` or `admin` roles, optionally limited to projects, for CI and teammates. Every deployment and control event records the acting credential name. See [Access control](access-control.md) for the endpoint table, the audit trail and a GitHub Actions deploy example. Control stores each credential's name, role, scope and public-key hash (never a private key); these records travel with control backups.
