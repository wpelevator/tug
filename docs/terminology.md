# Terminology

This page defines Tug's vocabulary and records the naming review of 1 November 2026. Definitions describe the current implementation. Interface changes below are recommendations, not commands or configuration available today; the [CLI reference](cli.md) documents the current interface.

## Core concepts

Tug has a control plane and managed nodes. Each node runs an agent, which connects to the control plane and manages that node's containers. Operators use the `tug` CLI to deploy projects made up of Compose services.

| Term | Meaning in Tug | Usage guidance |
| --- | --- | --- |
| Control plane | The central software: API, state store, deployment coordination, image builds and delivery, certificate issuance and backup scheduling. | Use the full name in prose; **control API** specifically means its HTTP/WebSocket interface. Existing `control-*` commands and the `control` runtime mode abbreviate it. |
| Control-plane host | The machine running the control plane. | Distinguish the machine from the software. Installing the control plane does not automatically register a workload node. |
| Node | A registered Docker host on which Tug places services, represented by a stable record. | Use for placement, addresses, labels, connectivity and lifecycle operations. The record remains when its agent stops or its identity is replaced. |
| Agent | The process/container on a node that fetches work, reconciles containers through the Docker Engine API, reports status and handles operations. | Use for software behavior, logs, configuration, upgrades and connections. A node runs an agent. |
| Host | An underlying Linux machine, whether or not registered with Tug. | Use in OS, SSH, Docker and resource discussions; use **node** for a managed deployment target. Qualify hostname fields separately. |
| Project | A named application instance grouping services, secrets, deployment history and volume records. | Keep the Compose term. Different projects can represent separate installations of the same application. Project scope is not host or tenant isolation. |
| Service | A named Compose component, such as `web` or `db`, run on selected nodes. | Keep the Compose meaning; this is not a Kubernetes Service networking object. |
| Replica | One steady-state running copy of a service on a selected node. | Currently at most one steady-state copy per project/service/node; rolling replacement temporarily overlaps old and new containers. |
| Placement | The selection of nodes on which a service runs. | Names pin nodes; labels select matching nodes when deploying or scaling. Do not imply continuous rescheduling or resource-aware scheduling. |
| Deployment | A recorded attempt to publish and converge a project's desired state, with its own ID and lifecycle. | Use for the operation/history record, including a rollback deployment. |
| Desired-state revision | The immutable identity of a desired-state record. | Deploy and rollback use their deployment ID as the revision; scaling can create a separate revision. Distinguish this from a display version. |
| Display version | The supplied or generated label shown for a deployment; current option: `deploy --version`. | It can be reused; it is not an image digest or the installed Tug version. |
| Rollout | Applying a desired-state change to running services. | A deployment has a rollout; `recreate` and `rolling` are service rollout strategies. |
| Service revision | A particular rendered service configuration, identified by a configuration hash for rolling replacement. | Qualify **revision**: this differs from a project's desired-state revision. |
| Ingress | The managed HTTP reverse proxy, currently Caddy, and its hostname routes. | Introduce as **HTTP ingress (managed reverse proxy)**. An ingress node has this capability; it is not a separate machine type. |
| Mesh | The optional WireGuard network between nodes. | Introduce as **private WireGuard network**. It does not make local volumes shared. |
| Operator credential | A certificate, private key, pinned CA and public control-plane URL used by a person or automation. | Current management commands are `token-*`, but transport uses mTLS. **Operator** includes CI. |
| Node identity | The registered node principal and authorized public key; its agent holds the private key and certificate. | Certificate renewal keeps the key. Identity replacement changes it and invalidates certificates for the old key. |
| Join key | The encoded, short-lived bootstrap credential and node binding used for self-service enrollment. | Explain as an **enrollment credential** containing private-key material. Current variables: `TUG_JOIN_KEY` and `TUG_JOIN_KEY_FILE`. |
| Workload backup | A restic snapshot of a configured service command's output or a volume's files. | Distinguish target, backup run and resulting snapshot. |
| Control-plane backup | An archive of Tug's control-plane state and retained artifacts. | Current command: `control-backup`. It does not capture workload volume contents. See [Control plane](control-plane.md#backup-and-restore). |

## Review findings

Priorities describe operator confusion, not security severity. High-priority items misdescribe an operation's target, authentication or infrastructure capabilities.

| Priority | Evidence in the current source | Confusion | Recommendation |
| --- | --- | --- | --- |
| High | `src/cli.ts`: `token-create` creates an operator credential; `token-list` lists API tokens. README and `docs/architecture.md` still describe bearer tokens. | Readers expect an API key or bearer workflow, while the implementation requires certificate credentials. | Standardize on **operator credential** for the distributed secret and **operator identity** for its named principal. Rename `token-*` to `credential-*`, updating `/api/v1/tokens`, protocol types, errors, persistence names and audit events together. Reserve token for an actual token mechanism. |
| High | `doctor --nodes` says “every registered agent”; `--node` says “one agent”; `logs` says “assigned node agent”. `node-remove` mentions an agent token. | Machine, process and credential become interchangeable, obscuring what removal, health and repair affect. | Keep **node** and **agent** distinct. Say “diagnostics on every node” and “service container logs”; mention the agent when relevant, such as “check agent logs on node app1”. |
| High | `node-replace` installs a new key, retaining node ID, metadata and placement. `node-repair` moves corrupt credential documents aside and replaces identity. | The verbs suggest replacing a VPS or repairing arbitrary host/service state. | Prefer `node-replace-identity` and `node-repair-identity`, with help explaining SSH and agent restart. Keep `node-disable` for blocking authentication; explain that it withdraws service endpoints but does not stop containers or gracefully drain workloads. |
| High | `node-enroll` creates a join key and prints a command/cloud-init; the agent later calls `/agent/v1/enroll`. The response is `EnrollTokenResponse`. | Preparing enrollment and enrolling a host appear to be the same action. Join key, enrollment token and bootstrap certificate appear to be separate mechanisms. | Prefer `node-prepare-enrollment` for the operator command. Use **enrollment credential** for its bootstrap secret and **enrollment** for the actual agent flow; rename the response accordingly. Explain join key as the current encoded envelope. |
| High | `docs/networking.md` and `TUG_SERVICE_DNS` call the feature service DNS; implementation injects `extra_hosts`. | The name suggests a DNS server, round-robin answers, stable service endpoints or immediate updates beyond the hosts-file contract. | Use **cross-node service names (hosts-file entries)**; consider `TUG_SERVICE_NAMES` for the interface. Reserve **service DNS** for the proposed DNS implementation. Keep same-node Docker DNS distinct. |
| High | README says agents apply Docker Compose; architecture says Docker Engine API. Compose and networking docs retain descriptions of Compose projects and `compose up` from the earlier runtime. | Compose sounds like the execution engine on nodes, obscuring installation and troubleshooting requirements. | Describe Tug as **deploying Compose applications through the Docker Engine API**. Compose normalizes input on the operator machine; agents manage containers directly. Update runtime descriptions against the implementation. |
| Medium | Prose alternates between control, control plane and control host; the `tug-node` executable starts either `control` or `agent`. | Component, machine and executable blur together. The shared runtime sounds specific to workload nodes. | Use **control plane** and **control-plane host** in prose. Keep `control` as an explicit command prefix/runtime mode. Prefer `tug-runtime` for the shared executable and `tug` for the CLI. |
| Medium | `version`, `revision`, `observedVersion`, `observedRevision` and `rolloutRevision` describe different identities; top-level `--version` also prints the CLI version. | A reusable display label can be mistaken for convergence identity or image pinning. Revision can mean project state or service configuration. | Qualify **display version**, **desired-state revision**, **service revision** and **image digest**. Consider `deploy --release-label` for the display label without introducing another release resource. |
| Medium | `src/compose.ts` resolves label placement by matching labels, sorting node names and selecting nodes at deploy/scale time. It accepts both `x-tug.global` and `x-tug.placement.global`. | Replicas/global can imply several copies per host, automatic failover, resource balancing or automatic expansion onto new nodes. Two global locations add alternatives. | Keep **replicas** and **global**, documenting the one-copy-per-selected-node limit and resolution timing. Keep only `x-tug.global`, the documented location. Describe placement without promising an autonomous scheduler. |
| Medium | Node status uses `online`/`stale`, project health uses `serving`/`skipped`/`failed`, and service `rolloutState` includes `serving`/`held`. An old rolling revision can serve after a new one fails. | Online, healthy, serving and deployment succeeded can look like one condition. | Label **node connectivity**, **project apply result**, **service rollout state** and **deployment state** separately. Explain stale as no recent agent contact, not proof the machine is off. Explain skipped as an apply result. |
| Medium | `--address`, `--public-address`, `--public-url`, `--control-url`, `--agent-control-url` and ingress `host` refer to different endpoints. | Public address sounds like an application's endpoint but means the WireGuard endpoint. A connect override can look like a TLS identity change. | Name **node service address**, **WireGuard endpoint**, **control-plane public URL**, **CLI connect URL**, **agent connect URL** and **ingress hostname** explicitly. Consider `--service-address` and `--wireguard-endpoint`. Keep verification identity separate from routing. |
| Low | Node labels are string tags; Compose labels are container metadata. `TUG_ROLE` chooses runtime behavior, `--role` grants access, and ingress is also a role. | The same words describe different levels; Kubernetes users may expect key/value node labels. | Keep **node labels**, documenting string tags and AND matching; qualify **container labels**. Use **runtime mode**, **access role** and **ingress capability**; consider `TUG_MODE` for runtime selection. |
| Low | `backup-run`/`restore` concern workload data, `control-backup` concerns platform recovery, and `backup-key` prints a repository password. | Backup can imply complete disaster recovery; key does not identify the returned secret. | Qualify **workload backup** versus **control-plane backup**. Prefer `backup-repository-password` for escrow. Keep restic's **snapshot** and **repository** terms. |

## Industry alignment

Use Compose application vocabulary with conventional infrastructure vocabulary. These comparisons concern naming and do not imply equivalent scheduling, networking or availability guarantees.

| Primary reference | Established vocabulary | Recommendation for Tug |
| --- | --- | --- |
| [Kubernetes components](https://kubernetes.io/docs/concepts/overview/components/) | Control plane, worker nodes and kubelet as node software. | Keep the machine/process distinction. **Agent** fills the conceptual node-software role; introducing kubelet, pod or controller resource names adds unrelated concepts. |
| [Nomad glossary](https://developer.hashicorp.com/nomad/docs/glossary) | A client is an agent managing tasks; a node is a machine running a client agent. | **Agent** is an established process name. Avoid **client** for Tug nodes because the CLI is also an API client. |
| [Compose application model](https://docs.docker.com/compose/intro/compose-application-model/) | Project, service, network and volume. | Keep **project**, **service** and **volume**. Application can explain a project in plain language without becoming another resource type. |
| [Kamal servers](https://kamal-deploy.org/docs/configuration/servers/) and [proxy](https://kamal-deploy.org/docs/configuration/proxy/) | Servers grouped by role; a proxy forwarding HTTP traffic. | Explain a node as a registered server and ingress as a managed reverse proxy. Keep **node** canonical because server also means application software or the API server. |

Keep **Tug** and **tug** as product/CLI names. The tugboat explanation is optional branding; boats, captains or fleets would add vocabulary operators must learn. **Cluster** may describe one control plane and its registered nodes, but should not become another required configuration object or imply high availability or automatic failover. Avoid master/slave, a standalone worker resource, or introducing controller as another name for the control plane.

## Recommended order of work

1. Correct authentication and runtime descriptions first. These factual inconsistencies amplify naming confusion.
2. Apply this vocabulary to help, errors, status descriptions and documentation. Keep literal commands, paths and variables accurate until their implementations change. Example onboarding: “Install the control plane, add a node, then deploy your Compose project. Tug runs an agent on each node.”
3. Rename misleading interfaces as coherent changes: credential management; node identity recovery; enrollment preparation; hosts-file service names; then address flags and the runtime binary. Update API paths, protocol types, persistence names where relevant, templates, tests, docs and changesets together. This is a greenfield project; prefer direct renames over compatibility aliases or migrations.
4. Treat command grouping as a separate usability decision. The [current convention](cli.md#cli-architecture-and-naming) is flat kebab-case; `credential-create`, `node-replace-identity` and `node-prepare-enrollment` fit it. Grouping into `tug node install` or `tug credential create` can improve discovery, but does not itself fix ambiguous nouns or verbs.

This review implements no runtime, CLI, API or configuration rename. Future changes should test CLI help and errors, credential/identity lifecycle flows, enrollment output, config resolution and status semantics. Avoid brittle word-ban tests: agent and control remain valid in their defined contexts.
